ブランチ : feature/v18-background-crashreport (未コミット)

■ 依頼と対応
1. 最小化 / 後ろにある (バックグラウンド) 間はランタイムの処理を止め、電力と CPU / GPU を使わない … 対応
   - Engine.Run : 最小化中、または前の窓が自分のプロセスの物でない時は、Update・物理・アニメーション・UI・描画・Present を全部しない
     (同じプロセスのファイルのダイアログ / 箱が前にある時は止めない)
   - 止めている間は MsgWaitForMultipleObjectsEx (100 ms) でメッセージが来るまで眠る
     (以前は最小化中だけ Thread.Sleep(16) で 1 秒に 60 回起き、後ろにある時は全部動いていた)
   - 音 : Audio.dll に Audio_Suspend / Audio_Resume (XAudio2 の StopEngine / StartEngine) を足し、止めている間は音の処理のスレッドも止める
     (再開すると続きから鳴る)。パッドの振動も止める
   - 再開した時は Time.ResetFrameClock で止めていた時間を DeltaTime に入れない (PlayTime も進まない)
   - 設定 : Engine.RunInBackground (既定 false。Unity の Run In Background と同じ)。true でも最小化中は以前と同じく止める
       Player : player.json の RunInBackground (Build Game の窓の「Run In Background」)
       エディター : View > Run In Background (exe の隣の editor_prefs.json に覚える)
       自動の確認 (--editor-test / --quit-after / Player の --frames) は常に true (他の窓を使っている間も進めるため)
   - Engine.IsInBackground / Engine.BackgroundChanged、Console に [Engine] Paused (in background / minimized) / Resumed after N s

2. クラッシュした時の原因を調べるためのクラッシュレポートを自動で作る … 対応
   置き場 : Player = exe の隣の CrashReports (書けなければ %LOCALAPPDATA%\Tsumugi Engine\CrashReports\Player)
            エディター / ランチャー = %LOCALAPPDATA%\Tsumugi Engine\CrashReports\<Editor|Launcher>
            1 回も落ちなければフォルダは残さない。新しい 10 個だけ残す
   中身 : Crash_yyyyMMdd_HHmmss/
     report.txt : C# の例外 (全文 / 内側 / スタックと行)、エンジンの版、exe / 引数、OS、.NET、CPU、メモリ、起動からの時間、
                  今のシーン、再生中か、エンジンの様子 (フレーム数 / dt / エンティティ数 / 後ろにあるか 等)、読み込んだ DLL と版 (ドライバーの版も分かる)
     native.txt : C++ で落ちた時。例外のコード、アドレス (モジュール + オフセット)、アクセス違反の読み書きと番地、
                  C++ のスタック (PDB があれば関数名と行)、シーン / 再生中か
     crash.dmp  : ミニダンプ (Visual Studio で開くと落ちた所が見える)
     log.txt    : そのセッションのログ (Console の出力。C++ のログも)。行ごとにファイルへ書いているので C++ で落ちても残る
   落ちた後 : 箱でレポートの場所を知らせ、フォルダを開ける (自動の確認では出さない)
   エディター : WinForms のイベント (ドラッグ & ドロップ 等) の中の例外は、レポートを書いて続ける (落とさない)
   確認用 : --crash-test managed|native|thread|stackoverflow (Player / エディター / ランチャー。10 フレーム後にわざと落とす)

■ しくみ
- C# : GameEngine.Runtime/CrashReporter.cs (AppDomain.UnhandledException / WinForms の例外 / 呼ぶ側の catch → Report)
  ミニダンプは dbghelp.dll の MiniDumpWriteDump。ランチャーは Runtime を参照しないので、このファイルだけ入れている (C# の例外だけ)
- C++ : Core.dll の Core/Source/Crash/crashHandler.cpp (crashDll.cpp で Crash_* を export)
  - SetUnhandledExceptionFilter : C++ だけのスレッド等で受け取られなかった例外
  - ベクター例外ハンドラー : 確認で分かったこと → C# から呼んだ C++ の中 (P/Invoke の先) のアクセス違反 / スタックオーバーフローは、
    .NET が FailFast で終わらせ、上のフィルターも AppDomain.UnhandledException も呼ばれなかった (最初の実装では何も残らなかった)。
    なので最初に呼ばれるベクター例外ハンドラーでも受け取る。C# の null 参照なども内部ではアクセス違反として起きるので、
    「落ちた所がネイティブの DLL (JIT のコード / C# のアセンブリ / coreclr / clrjit / ntdll / kernel32 / kernelbase 以外)」の時だけにした
  - 書くのは起動時に作っておいた別のスレッド (落ちたスレッドはスタックが残っていない時がある)。落ちたスレッドは頼んで待つだけ
  - C# が書いた後 (Crash_SetHandled) / 1 回書いた後は書かない (同じクラッシュで 2 つ作らない)
- 新しく使うライブラリ : dbghelp.dll (Windows に入っている。承認済み)

■ 確かめていない / 制限
- RunInBackground = true の時に後ろでも動き続けること (コードの分岐だけ。後ろに回す確認は既定 (false) だけ行った)
- ランチャーのクラッシュレポートは、ビルドだけ (起動して落とす確認はしていない。窓と箱が前に出るため)
- 受け取れない物 : C# のスタックオーバーフロー (.NET がすぐ終わらせる)、Environment.FailFast、各 DLL の CRT (/MT) の abort / 純粋仮想関数の呼び出し
- ベクター例外ハンドラーは「最初の機会」の例外を見るので、ネイティブの DLL が自分で __try で受け取るアクセス違反があると、
  落ちていなくてもレポートを作ることがある (OS の基本の DLL は除いた。エディターのテスト全体では起きなかった)
- ミニダンプは小さい形 (スタックと参照先のメモリ。約 1〜3 MB)。C# のヒープの中身は入らない (C# の例外の中身は report.txt にある)
