■ 今の状態 (調べた結果)
  できている物
    - ECS (Entity / ComponentPool<T> (struct) / ISystem / IFixedSystem)、エンジン組み込みの System
    - コンポーネント : Transform / Static / MeshRenderer / Camera / FreeCamera / OrbitCamera / DirectionalLight / PointLight /
                       AudioSource / Collider / Rigidbody / Joint / ParticleEmitter
    - 描画 (Forward / Deferred、PBR、SSAO、影、AA、GPU パーティクル)、衝突判定、物理、音、ゲームパッド
    - ImGui は C++ (RHI の debugUI) にあり、プロファイラー (F1) だけに使っている
    - 窓は C# の WinForms (Form) に D3D12 のスワップチェーン
  足りない物 (エディターに要る土台)
    - シーンはコード (Program.cs / Samples) で作るだけ。保存 / 読み込みが無い (シリアライズが無い)
    - エンティティに名前 / 有効・無効 / 親子が無い (Transform は平らで、親が無い)
    - アセットはパスで読むだけ (GUID / 依存 / 再読み込みが無い)。コンポーネントは C++ のハンドル (Model / Sound など) を直接持つ
    - 型の情報 (どのコンポーネントがあり、どの値を見せて変えられるか) をまとめた所が無い
    - 描画 / 物理 / 時間 などの設定は、コードから engine.Graphics.* / engine.Physics.* を書くだけ (シーンやアセットに保存されない)
    - ゲームのコード (Samples) とエンジンが同じ exe。編集中 / 実行中 の区別が無い

■ 決めておきたいこと (着手前。おすすめを先に)
  1. エディターの GUI
     a. ImGui を C# から使う (ImGui.NET + docking。描画は自前の RHI へ)  ← おすすめ
        ゲームエンジンのエディターで一番よく使われる形。インスペクターを型の情報から自動で作りやすく、
        ユーザーの拡張 (独自のインスペクター / ウィンドウ) も C# で書ける。NuGet の取得 (ダウンロード) の許可が要る
     b. C++ の ImGui を C ABI で 1 つずつ出す : 外部の取得は要らないが、出す関数が数百になり、拡張が C++ 側に寄る
     c. WinForms / WPF のエディター + 真ん中に D3D12 の画面 : PropertyGrid などがすぐ使えるが、ドッキングや
        ゲーム内の UI と分かれ、見た目と操作感がゲームエンジンらしくない
  2. シーン / アセットのファイル : JSON (テキスト。差分が見やすく、手でも直せる)  ← おすすめ。後で読み込みの速いバイナリも作れる
  3. exe の分け方 : Runtime (今の GameEngine.Runtime) / Editor (新しい exe) / ゲームのコード (ユーザーの DLL) / Player (出来上がったゲーム)  ← おすすめ
     (今の GameEngine_console は見本として残し、少しずつシーンのファイルへ移す)
  4. ゲームのコードの読み直し (ホットリロード) : エディターを閉じずに、ゲームの DLL をビルドして読み直す
     (AssemblyLoadContext を捨てられる形で使う)。ビルドは MSBuild (dotnet build は COM 参照で失敗するため)

■ 段階 (今までと同じく、段ごとに見た目 / テストで確認してマージ)

  ED1 : 型の情報とシリアライズ (GUI なし。全部の土台)
    - コンポーネントの登録 : 型ごとに「見せる値 / 保存する値」の一覧を作る (属性で指定 : [SerializeField] [HideInInspector]
      [Range] [Tooltip] [Header] など。Unity と同じ考え方)。起動時に 1 回だけ作り、ゲーム中はリフレクションを使わない
    - エンティティに名前 / 有効・無効 / 安定した ID (GUID。保存しても変わらない) を付ける
    - シーンの保存 / 読み込み (JSON)。エンティティへの参照 (Joint.ConnectedBody など) は ID で保存
    - アセットへの参照は GUID で保存 (Model / CollisionMesh / Sound / テクスチャ)。コンポーネントは「アセットの参照」を持ち、
      C++ のハンドルは System が引く形に (以前はハンドルを直接持っていた)
    - 確認 : 今の全部のコンポーネントで「保存 → 読み込み → 同じ値」のテスト。見本のシーンを JSON に書き出して読み直し、同じ絵になる

  ED2 : 親子 (階層) と、エンティティの扱い
    - Transform に親を持たせる (ローカル / ワールド。親が動くと子も動く。TransformSystem を親から順に計算する形に)
    - 物理 / 描画 / 音 / パーティクルはワールドの値を使う (今は Transform = ワールド)。剛体の子は親から外す扱いを決める
    - 確認 : 親を回すと子が付いて回る / 剛体・コライダー・ライトが子でも正しい / 1 万個の性能が落ちない

  ED3 : エディターの枠 (GUI が出る)
    - Editor の exe (Runtime を参照)。ImGui (決めること 1) を C# から描く (RHI に ImGui 用の描画を足す。フォントとテクスチャ)
    - ドッキングできる窓 : シーンビュー (描画パイプラインの結果をテクスチャにして表示) / 階層 (Hierarchy) / インスペクター /
      コンソール (ログ) / プロファイラー (今の C++ の F1 を移す)
    - インスペクターは ED1 の型の情報から自動で作る (数 / ベクトル / 色 / 列挙 / 真偽 / アセットの参照 / エンティティの参照)
    - 確認 : 見本のシーンを開き、物を選んで値を変えると、すぐ絵が変わる

  ED4 : シーンの編集
    - 選ぶ (シーンビューでクリック。GPU の ID バッファか、物理のレイキャスト) / 選んだ物の輪郭
    - ギズモ (移動 / 回転 / 拡大縮小。ローカル / ワールド。スナップ) / エディターのカメラ (今の FreeCamera を流用)
    - 作る / 消す / 複製 / 親を変える (階層のドラッグ) / コンポーネントを足す・外す
    - 元に戻す / やり直す (変更を「前の値 → 後の値」で記録する。ED1 のシリアライズを使う)
    - 再生 / 一時停止 / 1 フレーム進める / 停止 (停止で再生前のシーンに戻す。編集中は物理やゲームの System を止める)
    - 確認 : 物を置いて動かし、保存して開き直すと同じ。再生して止めると元に戻る。元に戻すが全部の操作で効く

  ED5 : アセット
    - Assets フォルダとアセットの一覧 (GUID と設定を .meta に)。取り込み (obj / pmx / png・jpg (DDS への変換は今の DirectXTex) / wav)
    - アセットブラウザ (サムネイル / フォルダ / 検索) / インスペクターやシーンビューへドラッグ
    - ファイルが変わったら読み直す (テクスチャ / モデル / シェーダー)。使っていないアセットの解放
    - マテリアルをアセットにする (今はモデルに付いた物だけ) : 色 / テクスチャ / 粗さ・金属
    - 確認 : 新しいモデルを Assets に置くと一覧に出て、ドラッグでシーンに置ける。テクスチャを描き直すとすぐ変わる

  ED6 : 今までの機能のコンポーネント化 (ご要望 2)
    コードの設定だった物を、シーン / アセット / プロジェクトの設定として、インスペクターから触れるようにする
    - 描画の設定 (パイプライン / ライティングのモデル / 環境光 / トーンマップ / 露出 / SSAO / 影 / AA / 背景の色)
        → シーンの「描画の設定」(RenderSettings) + 場所ごとに効くポストエフェクト (Volume。範囲に入ると混ぜる)
    - 物理の設定 (重力 / 解き方 / 眠り / レイヤーの衝突の表 / 並列のスレッド) → プロジェクトの設定 (ProjectSettings)
    - レイヤーの名前 / タグ / 固定の時間刻み / ゲームパッドとキーの割り当て (入力のアクション) → プロジェクトの設定
    - 音 (全体の音量 / 聞く位置 AudioListener)、カメラの操作 (FreeCamera / OrbitCamera) をコンポーネントとして整える
    - 確認用の表示 (コライダー / 接触点 / ジョイント / 影の段 / パーティクルの数) → エディターのギズモ / 表示の切り替え
    - 見本 (Showcase / 衝突判定 / 物理 / パーティクル) を、コードからシーンのファイルに移す (Spin などはゲームのコードとして残す)
    - 確認 : 見本のシーンをエディターで開くと、今までと同じ絵と動き。設定を変えて保存すると次も同じ

  ED7 : ユーザーによる拡張 (ご要望 1 の「任意の拡張化」)
    - ゲームのコードを別の DLL (ゲームのプロジェクト) に。エディターがビルドして読み直す (ホットリロード)。
      読み直しの前後でシーンを保存 / 読み込みして値を引き継ぐ
    - 自分のコンポーネント / System を属性で登録するだけで、インスペクター / 保存 / コンポーネントを足すメニューに出る
    - 独自のインスペクター ([CustomEditor(typeof(T))]) / 独自のウィンドウ ([EditorWindow] とメニュー) /
      シーンビューに描くギズモ (OnDrawGizmos 相当) / 独自のアセットの取り込み (拡張子ごと)
    - 確認 : ゲームのプロジェクトに新しいコンポーネントを書いて保存すると、エディターを閉じずに使える

  ED8 : プレハブと出来上がったゲーム (Player)
    - プレハブ (エンティティの塊をアセットに。置いた物は元の変更を受け継ぎ、変えた所だけ持つ)
    - ゲームの書き出し : Player の exe + シーン + 使っているアセットだけをまとめる (エディターの物は入れない)
    - 確認 : 書き出したゲームが、エディターの再生と同じ動き

■ 順番の理由
  - ED1 (型の情報とシリアライズ) が全部の土台 : インスペクター / 保存 / 元に戻す / 再生の巻き戻し / ホットリロード / プレハブが全部これを使う
  - ED2 (親子) はエディターで物を扱う前提なので、GUI の前に入れる (後から入れると、全部の System と保存の形を直し直すことになる)
  - ED6 (コンポーネント化) は ED1 の後ならいつでもよいが、エディターで触れる形 (ED3 / ED4) ができてからの方が確かめやすい
  - 性能 : エディターの物 (型の情報 / ID / 元に戻す) はゲーム中に重くならない形にする (リフレクションは起動時と編集時だけ)。
           今の計測 (1 万個の描画 / 衝突判定 / 物理) が落ちないことを段ごとに確かめる
