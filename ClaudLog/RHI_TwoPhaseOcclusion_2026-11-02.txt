====================================================================
 2 段階のオクルージョンカリング (カメラが動いた時の 1 フレームの遅れを無くす)
 日付   : 2026-11-02
 ブランチ : feature/two-phase-occlusion
====================================================================

■ 背景
  前回のオクルージョンカリングは「前のフレームの深度とカメラ」で Hi-Z を作って判定していた。
  そのため、カメラが動いて新しく見えるようになった物が、1 フレーム遅れて出ることがあった。

■ 2 段階の流れ (CommandContext::Render)
  1. 前段カリング (phase 1) : 前のフレームで見えていた物 (可視の記録 = 1) だけを、視錐台で判定して描く
  2. 前段の描画 (ExecuteIndirect)
  3. Hi-Z を作る : 前段の深度から (このフレームのカメラ)
  4. 後段カリング (phase 2) : 全部の物を視錐台 + Hi-Z で判定し直す
       - 見えている物を可視の記録に書く (次のフレームの前段で使う)
       - そのうち前段で描かなかった物だけを描く
  5. 後段の描画 (ExecuteIndirect)

  なぜ遅れが無くなるか :
    - Hi-Z はこのフレームのカメラ・このフレームに描いた深度から作るので、判定は常にこのフレームの状態で行われる。
    - このフレームで見えている物は、前段で描いた (前のフレームで見えていて視錐台の中) か、
      後段で描く (見えているのに前段で描いていない) のどちらかに必ず入る。
    - 前のフレームの結果は「どれを前段で描くか」を決めるだけで、描かれるかどうか (正しさ) には影響しない。
  ※前段で描いた物は Hi-Z に自分の深度が入っているが、自分の一番手前はそれより奥にならないので、自分で自分を隠すことは無い。

  可視の記録が使えない時 (描画リストが変わった / 前のフレームでオクルージョンしていない) :
    前段は何も描かず、後段で全部を判定する (そのフレームは Hi-Z が空 = 何も隠れないので、全部描く。正しさは同じ)。

■ 実装
  gpuCulling.shader
    - g_Phase (0 = 視錐台だけ / 1 = 前段 / 2 = 後段)、g_ResetVisibility を追加
    - g_Visibility (u3) : オブジェクト (DrawData の番号) ごとの可視の記録
    - 投影には、描画用と同じフレームの定数 (View / Projection、Root CBV b1) を使う
      (以前は Hi-Z を作った時の行列をルート定数で渡していた。ルートシグネチャは 63 → 52 DWORD に減った)
  CommandContext
    - recordCulling(phase, resetVisibility) : 前段・後段で 2 回呼ぶ。読み戻しも 2 回分 (表示は合計)
    - 後段の前に Culled を「読む状態 → UAV」へ戻す (前段の描画が読み終わるのを待つ)
    - buildHiZ は前段の描画の直後に呼ぶ (以前はシーンを描き終えた後)
    - _visibility (可視の記録)、_visibilityState / _visibilityValid を追加。前のフレームのカメラを覚える処理は削除
  Pipeline : カリングのルートパラメータに CULL_PARAM_VISIBILITY (u3)、CULL_PARAM_FRAME (b1)
  Buffer   : GetViewProjectionForShader (前回追加) は不要になったので削除

  途中で出たエラー :
    前段では Hi-Z を読まないが、ルートには設定する。D3D12 のデバッグレイヤーは設定しただけで「使った」とみなして
    暗黙の昇格 (COMMON → NON_PIXEL_SHADER_RESOURCE) をしたことにするため、Hi-Z を作る時の遷移バリアが食い違った。
    → 前段でも、ルートに設定する前に明示的にその状態へ移すようにした。

■ 計測結果 (RTX 2070 / Release / 1280x720 / ExecuteIndirect + インスタンシング + GPU カリング、各 2 回)
                                   オクルージョンなし   1 段階 (前回)   2 段階 (今回)
    地面すれすれ (1010 / 14850 個)     0.178 ms           0.115 ms        0.135 ms
    格子の中から (隠れる物なし)        0.105 ms           0.153 ms        0.171 ms
    全体が映る (隠れる物なし)          0.203 ms           0.247 ms        0.267 ms
    通常起動 (箱 1 個)                 0.038 ms           0.075 ms        0.087 ms

  正直なまとめ :
    - 2 段階は 1 段階より 約 0.02 ms 重い (カリングがもう 1 回、フレームの途中で「描画 → コンピュート → 描画」の待ちが 1 回増える)。
    - その代わり、カメラが動いても新しく見えた物が遅れて出ることが無い (毎フレームの結果がそのフレームだけで正しい)。
    - 隠れる物が多い場面では、オクルージョンなしより 24% 速い。

■ 確認したこと
  - D3D12 デバッグレイヤーのエラー・警告 0 : 通常起動 / 地面すれすれ (ON・OFF) / 格子の中から / 全体 /
    インスタンシングなし / 1 個ずつ描く / GPU カリング OFF
  - 地面すれすれ・格子の中からの 2 つのカメラで、オクルージョン ON / OFF の画面がシーンの範囲 142000 ピクセルで一致。
  - プロファイラーの Visible (GPU) / Draw calls (GPU) は前段と後段の合計 (地面すれすれで 1010 個 / 252 描画。前回と同じ)。
  ※動くカメラでの確認 : 今のテストにはカメラを動かす機能が無いので、画面では確かめていない。
    上の「なぜ遅れが無くなるか」の通り、各フレームの判定はそのフレームの状態だけで行うので、静止したカメラで正しければ動いても正しい。

■ この先の案
  - 深度バッファを直接 SRV で読む (深度の写しを無くす。約 0.012 ms)。
  - 前段の描画が少ない時 (= ほとんど何も見えていなかった) は、後段だけにする などの負担の削減。
  - 負荷テストにカメラを動かすモードを足す (動いている時の見た目と負担を確かめるため)。
