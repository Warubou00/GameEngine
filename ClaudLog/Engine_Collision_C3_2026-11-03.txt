■ 何が重かったか (最初に測った内訳。10,000 個・全部動く)
  - Step のほとんどがブロードフェーズ (3.7〜4.7 ms)。木の節の組をたどる時間
  - 見えていなかった時間 : SetTransforms の中で、はみ出した葉を 1 つずつ抜いて入れ直す (1.24〜1.48 ms)
    → 計測に Sync (SetTransforms) / Tree (木を直す) / Events / C# の合計を足した (PhysicsStats 32 → 48 byte)

  1. レイヤーの衝突の表 (ご提案の、静的なレイヤーのビットで調べるかを決める方法)
     - engine.Physics.SetLayerCollision(a, b, bool) / IgnoreLayerCollision / GetLayerCollision (Unity と同じ)
       体ごとの Collider.CollideWith と、両方で許された組だけ調べる。既定は全部のレイヤーどうしを調べる
     - C++ は体の「当たる相手」= CollideMask & 表[レイヤー] を持ち、組を調べる前にビットの AND で落とす
     - 木の節に「枝の中のレイヤー (OR)」と「枝の中の物が当たる相手 (OR)」を持たせ、当たりえない枝は
       箱を調べる前にまるごと飛ばす (問い合わせ / レイ / 組を探す全部で使う)
     - 効果 : 計測ではレイヤーが空間に混ざって置かれているので、木での間引きの効果は小さい (7% ほど)
       表で外した組は形の判定から消えるので、レイヤー 8 個なら候補 2,910 → 1,038 / 形の判定 0.36 → 0.12 ms
       レイヤーが場所で分かれている時 (地形 / 弾 / UI のトリガーなど) は、木での間引きがよく効く
  2. 木の作り直し (DynamicTree::Rebuild)
     - SetTransforms では、はみ出した葉の箱を広げ、上の節の箱を広げるだけ (EnlargeProxy。木の形は変えない)
     - Step の始めに、はみ出した葉が動く物の 1/16 以上なら中の節を全部作り直す。少なければ 1 つずつ入れ直す
     - 作り直した木の方が質が良く、組をたどる時間も 4.4 → 2.1 ms (1 つずつ入れ直す木は偏ってくる)
  3. 組の表 (Box2D の pair / Bullet の pair cache と同じ考え方)
     - 太らせた箱が重なっている組を、Step をまたいで持ち続ける (開番地法のハッシュ表 + 続いた配列)
     - 新しい組ができうるのは、太らせた箱が変わった体の所だけなので、毎 Step 探すのはその体だけ
       (変わった体が動く物の 1/4 以上なら、木の節の組を 1 回たどって全部を探し直す)
     - 形の判定は、表の組のうち、どちらかが動いた組だけ。接触も組が持つ
     - 以前は毎 Step、動いた体から組を探し直し、unordered_set / unordered_map の表と比べていた
  4. 動いた向きに太らせる : 前の箱の中心からのずれ × 4 だけ、動いた向きに箱を広げる (Box2D の aabbMultiplier)
     まっすぐ動く物はしばらく箱の中に収まり、木を直す回数も、新しい組を探す回数も減る
     瞬間移動で大きくならないよう、広げる量は箱の大きさまで
  5. 並列化 (jobSystem.* : 常駐のワーカースレッドで ParallelFor。呼んだスレッドも働く)
     - 形の判定 (組ごとに別の所へ書く) / SetTransforms の形と箱の作り直し (体ごと) / 木の作り直し (上の 3 段の後の 8 本の枝)
     - 既定のスレッド数 : 論理コアの数 - 1 (3 本まで。描画と C# の分を残す)。engine.Physics.SetWorkerCount(n)
     - 木の問い合わせは、木が持つ作業用の配列をやめ、関数の中のスタックにした (同じメッシュの木を並列に問い合わせるため)
  6. 木の作り直しの方法
     - 節ごとに一番広がった軸の真ん中で分ける (nth_element) : 1 万個で約 1.15 ms (並列でも半分にしかならない)
     - Morton 符号 (中心の座標のビットを交互に並べた数) で 1 回だけ基数ソートし、違う一番上のビットで分ける (Karras 2012)
       : 約 0.59 ms。木の質はほぼ同じ (数の真ん中で分けると質が落ちて、組をたどる時間が 2 倍になった)
     - 作り直す境目 : 1/4 → 1/16 (作り直しが安くなったので、早めに作り直した方が良い)

■ 試してやめた物 / 比べる用に残した物 (Physics_SetOption)
    1 : 木の節のレイヤーのビットで枝を飛ばす (既定 1)
    2 : 追加のスレッドの数 (既定 論理コア - 1、3 本まで)
    3 : 多く動いた時に木を作り直す (既定 1)
    4 : 全部の組を探し直す境目 1/N (既定 4)
    5 : 動いた向きに広げる倍率 (既定 4。8 だとまっすぐの計測ではさらに速いが、組が増えるので 4 にした)
    6 : 木を作り直す境目 1/N (既定 16)
    7 : Morton 符号の順で作り直す (既定 1)
  - グリッドは比べる用のまま (1 万個で BVH の 5 倍遅くなった。BVH とグリッドを自動で選ぶ必要は無くなった)

■ 確認
  - Physics.dll のテスト (DLL を直接呼ぶ。Release / Debug とも) : C1 の 39 項目 / C2 の 33 項目 すべて OK
  - BVH / Brute (全部の組) / Grid で、毎 Step の重なりの数とイベントの数が全部同じ (2,000〜3,000 個、200 Step、
    まっすぐ / ふらふら / 5% 動く / レイヤー 4 個。Release / Debug とも)
  - Debug (D3D12 デバッグレイヤー有効) で D3D12 のエラー / 警告 0
      見本 (イベントの表示あり)、計測 2,000 個 + 線 + レイヤー 4 個、計測 1,500 個 (グリッド) + 線
  - Debug の Step は 2,000 個で 2.7 ms (最適化なしのため。Release の約 20 倍)

■ 制限 / 次
  - 計測の動きは単純 (まっすぐ / ふらふら)。物理 (P1) で積み重なって止まっている物が多い時は、動いた物が少ないので速い方
  - 同じ体を 1 回の SetTransforms で 2 回渡さないこと (並列で同じ体を書くため)。CollisionSystem は 1 回ずつ送っている
  - 次は P1 (固定の時間刻み + 剛体 + 押し戻し)
