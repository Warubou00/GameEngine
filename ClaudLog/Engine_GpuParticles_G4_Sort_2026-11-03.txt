GPU パーティクル G4 : 奥行きのソート (バイトニックソート) (2026-11-03)
==========================================================================

--------------------------------------------------------------------------
1. 仕組み (particleSim.shader の CSParticleSort* / CommandContext::sortParticles)
--------------------------------------------------------------------------
 - キー : 更新でカメラからの奥行き (正の float のビットをそのまま uint で比べる)。生きている物は必ず 0 より大きくする
 - 並べる長さ N : 生存数の上限 (2 フレーム前に読み戻した生存数 + その後 2 フレームに頼んだ出す数) 以上の 2 の累乗 (1024 以上)
   (資料は全エミッターの最大数の合計から段数を決めていた。ここでは CPU が知っている数で上限を絞る)
   生存数より後ろは キー 0 として読み、末尾 (一番手前) に集める
 - Dispatch : SortLocal (1024 個ずつ共有メモリで全部) → k = 2048〜N ごとに SortStep (距離 1024 以上) × 段 + SortMerge (距離 512〜1 を共有メモリ)
   N = 2^n で 1 + Σ(k=11..n)(k-9) 回。2^18 で 45 回 / 2^20 で 66 回
 - 半透明のエミッターが 1 つも無い時はソートしない (加算は並び順に関係なく同じ色 : 資料の高速化案)
 - Graphics.Particles.Sorting で ON / OFF (見本は P)

--------------------------------------------------------------------------
2. 計測で見つけた問題と直し
--------------------------------------------------------------------------
 - 最初は出力の生存リストをその場で並べていた。その列が次のフレームの入力になるので、更新がパーティクルを奥行きの順
   (メモリの上ではばらばら) に読むことになり、キャッシュが効かなかった
   (Release / RTX 2070 / 100 万個 : 更新 (ソートを除く) ソートなし 1.646 ms → ソートあり 2.935 ms)
 - 直し : 並べる先を「このフレームの更新で使い終わった入力のリスト」にする (SortLocal が出力から読んで写しながら並べる)。
          描画は並べた写しを読み、次のフレームの入力は出力 (生まれた順に近いまま) を使う。バッファは増えない
   結果 : 100 万個 更新 2.93 → 1.76 ms / フレームの GPU 7.33 → 6.33 ms。50 万個は 0.98 → 0.96 ms (小さい時は差が小さい)

--------------------------------------------------------------------------
3. 確認
--------------------------------------------------------------------------
 - --scene particles --view smoke (Debug、エラー 0) : ソートあり / なし を比べた
   ソートなしは、根元の新しい (色の濃い) 煙が奥にあっても手前に描かれて黒っぽい塊が出る。ソートありは奥から順に重なる
   (scratchpad/g4sorton_t9.png / g4sortoff_t9.png。直した後も g5dsceneparticlesviewsmoke_t8.png で同じ見た目)

--------------------------------------------------------------------------
4. 残っている課題 (最適化は保留中のため、計測だけ)
--------------------------------------------------------------------------
 - 100 万個 (N = 2^20) のソートが 3.4 ms と重い。2^19 (0.89 ms) からの伸びが 2 倍を大きく超えるのは、1 回の段で読み書きする
   8MB が L2 (4MB) に収まらなくなるため と思われる (未検証)
 - 案 : 共有メモリで並べる長さを 2048 に増やす / 半透明の物だけを別の列にして並べる (加算は並べない) /
        エミッター単位のソート (資料の案) / 基数ソート (onesweep)
